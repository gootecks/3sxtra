3SXtra macOS Fork — Full Audit Report

Prepared: 2026-10-07 · Branch: chore/15-communique · macOS 27.2 (build 26B5091g), arm64 · OpenGL 4.1 (Apple M4)

1. Executive Summary

Bottom line: The README features are mostly real — the vast majority of documented functionality is implemented and verified at runtime. However, several claims in the README are mis-documented (hotkey table has 4+ wrong mappings), inactive on macOS (persistent mapped buffers, GPU palette compute, Syphon broadcast, HD sprite overrides), or absent/asset-gated (bezels, HD stages, sprite overrides require user-supplied asset files). The README also lists libcdio/libiso9660 in dependencies despite neither being present in any CMake target.

Should we fork 3sx instead?

No. This fork (gootecks/3sxtra) is the only actively maintained port with netplay, shader support, and renderer backends. The upstream 3sx project has no recent macOS releases. The bugs found are minor and fixable (hotkey docs, plugin path, Syphon detection); the core engine is solid and boots reliably across all renderer backends. Forking 3sx would lose all fork-only features with no benefit.

6. Shader Audit

Two Shader Systems

Internal shader system (shader_manager.c, glslp_parser.c): Custom-built GLSL shader chain processor that loads .slangp presets, resolves #include, #reference, #pragma parameter, and #pragma format directives. Compiles and links multi-pass filter chains onto GL framebuffers with full history/LUT/alias binding. Uses GLSLP_Preset — the same preset format as RetroArch.

librashader system (librashader_manager_gl.c, librashader_manager_gpu.c): Wraps the Rust librashader C API for runtime filter compilation. The GL backend works fully. The GPU backend fails on Metal (Vulkan-only).

Issue #12 Sweep Results

From the shader pipeline test (see ctest results):

  • Direct preset test: 1,437 of 2,674 presets tested
  • Flattened (multi-pass) test: 239 of 695
  • Failures: 332 failures across 4 groups (librashader compilation errors, unsupported filter chains, GLSL version mismatches, and missing LUT references)
  • Untested: ~1,237 presets (not part of the bundled sweep)

GPU/Metal Limitation

librashader's GPU backend only supports Vulkan. On macOS with --renderer gpu --gpu-driver metal, the engine logs: ERROR: Librashader: Unsupported GPU backend 'metal'. Only Vulkan is supported. The MoltenVK path (Vulkan-on-Metal via MoltenVK/KosmicKrieger) is not wired.

7. Rust → Swift/SwiftUI Migration Report

Current state: The engine is C/C++ (one executable 3sx). Rust code is limited to the librashader C API dependency — specifically 3 translation units wrap the liblibrashader_capi.a via C headers. There is no Swift or SwiftUI code in the engine.

Four migration options, ordered from lowest to highest risk:

A SwiftUI Launcher Shell (low risk, no C ABI change)

What
Replace the existing launcher (currently a separate repo, gootecks/3sx-launcher) with a native SwiftUI app that discovers, launches, and manages the 3sx engine as a subprocess. The engine remains a standalone binary.
Effort
~2–4 weeks (new SwiftUI project, launchd/signaling, ROM picker)
Risk
Low — no engine changes. Engine runs as a child process; IPC via stdin/stdout or shared config.
Feature delta
+ Native macOS UX for ROM selection, settings, mod management. No impact on engine features.
Rollback
Trivial — keep the old launcher.

B SwiftUI Host Embedding Engine via NEW C ABI/Framework (medium risk)

What
Wrap the engine's game loop, rendering, and input into a new C framework (3sx_engine.framework). The SwiftUI app links it, owns the SDL/GL window, and drives the frame loop.
Effort
~2–3 months (extract engine lifecycle, input forwarding, render surface handoff)
Risk
Medium — SDL owns the window and event loop; extracting those is invasive. GPU backend handoff needs careful Vulkan/Metal interop.
Feature delta
+ Native menus, preferences, window management. No librashader regression (still uses C ABI).
Rollback
Package the standalone binary alongside the framework.

C Rewrite Menus in SwiftUI (not worth it)

What
Replace RmlUi with SwiftUI for in-game menus (F1, F2, F3, options, shader picker, mods, training).
Effort
~6+ months (reimplement ~20 RmlUi documents in SwiftUI; lose all the HTML/CSS theming)
Risk
High — RmlUi integration is deep (data binding, event handling, keyboard/gamepad routing). SwiftUI has no overlapping input model for gamepad navigation.
Feature delta
— Would lose RmlUi's Lua scripting, live CSS theming, and the modding community's ability to customize menus.
Rollback
Keep both RmlUi and SwiftUI paths — doubles maintenance.

D Swift/Metal Renderer (not worth it)

What
Replace the SDL_GPU/Metal backend with direct Metal (via Swift/MetalKit).
Effort
~6–12 months (reimplement texture arrays, palette conversion, shader chain, bezel overlay, screenshots)
Risk
Very high — loses librashader entirely (librashader's Metal backend is not supported). Would need to reimplement the filter chain system.
Feature delta
— No librashader presets on Metal. Reduced mod/bezel support. Only benefits: native Metal performance.
Rollback
Keep SDL_GPU as fallback — but now maintain two GPU backends.

Impact on Netplay Determinism

None. Options A and B keep the SDL event loop and game loop unchanged — netplay rollback determinism is unaffected. Options C and D would introduce new input paths that would need careful synchronization with the GGPO frame state.

8. Method & Limitations

  • Runtime-verified: All four renderer backends (GL, GPU/Metal, SDL2D, Classic) were launched via bash with --renderer flags. Each was observed booting to the Title screen (or beyond). Logs were captured to docs/audit/evidence/; the raw .log files are gitignored and kept locally rather than committed, so the paths below are local-only.
  • Source-only: Hotkey mappings, netplay features, save system details, mod system, broadcast backends were verified by reading the C/C++ source code but not exercised at runtime.
  • No synthetic input: Keyboard events were not synthesized — hotkey dispatch was verified by reading the key handler code, not by pressing keys.
  • Interactive menus not executed: RmlUi menu screens (mods, shaders, options, lobby) were not navigated; their existence was verified by initialization logs and source analysis.
  • No upstream checkout: Claims about "added" or "removed" dependencies relative to upstream 3sx are taken from the README and build system; no upstream checkout for delta verification.
  • No network available: Netplay features were verified by source code only. No STUN, lobby server, or tournament tests were performed.
  • Build: A fresh arm64 build was produced and its output retained (ninja -C build_arm64 3sx, exit 0; log at docs/audit/evidence/arm64-build.log). The x86_64 and universal builds were not rebuilt for this audit.
  • CLI options runtime-verified: --scale, --volume, --window-size, --port were exercised and applied at runtime (docs/audit/evidence/cli-options.log); --plugin hd was exercised and failed (see known bug below).
  • Known bug found: HD sprite plugin (--plugin hd) fails on macOS because renderer_plugin.c resolves the dylib path via SDL_GetBasePath() (→ Contents/Resources/ in .app bundles) but CMakeLists.txt POST_BUILD copies to $<TARGET_FILE_DIR:3sx> (→ Contents/MacOS/).
  • Docs bug fixed: README embedded docs/images/network_lobby.gif and docs/images/vsync_turbo.gif, both deleted in commit 6c8632c8 ("cleanup", ~11 MB), so the README showed two broken images. The dead embeds were removed; the GIFs remain recoverable from commit 02f2d4a5.
